# 周边去哪儿：基于高德的地点推荐助手

## 一、Skill 概述

本 Skill 引导 Agent 基于**高德地图 MCP Server** 完成"提出需求 → 查询高德 → 返回推荐"的完整流程，为用户推荐起点附近符合需求的地点，并提供步行距离与预计耗时。

### 适用场景
- 用户想在当前位置或指定起点附近找咖啡馆、餐厅、公园、便利店等
- 用户对步行时间有明确限制（如"步行不超过 15 分钟"）
- 用户需要最多 N 个候选地点，并按距离优先或其他偏好排序

### 不适用场景
- 多站串联路线规划（本题要求各地点为同一起点的独立备选）
- 驾车/公交等非步行方式（本 Skill 仅使用步行路线规划）
- 跨城市或极远距离推荐（步行 100km 以外高德不支持）

---

## 二、可用高德工具

评测平台已为你配置官方高德 MCP Server（`@amap/amap-maps-mcp-server`），以下是你需要用到的工具，**直接调用工具名即可，无需自行配置 API Key**。

### 核心工具一览

| 工具名 | 用途 | 必填参数 | 返回关键字段 |
|--------|------|----------|-------------|
| **`maps_around_search`** | 周边搜索：以起点为中心、指定半径内搜索 POI | `location`（中心点经纬度 `lng,lat`）、`keywords`（地点类型关键词）、`radius`（搜索半径，米） | `pois` 列表，每个 POI 含：`name`、`address`、`location`（经纬度 `lng,lat`）、`type`、`id` |
| **`maps_text_search`** | 关键词搜索：按关键词和城市全局搜索 POI | `keywords`、`city`（城市名或 adcode） | 同上，返回 `pois` 列表 |
| **`maps_direction_walking`** | 步行路径规划：计算从起点到候选地点的步行路线 | `origin`（起点经纬度 `lng,lat`）、`destination`（终点经纬度 `lng,lat`） | `route.paths[0]` 含：`distance`（步行距离，米）、`duration`（步行耗时，秒）、`steps` |
| **`maps_distance`** | 距离测量：批量测量多个候选到起点的步行距离和时间 | `origin`（起点）、`destination`（终点，多个用 `|` 分隔）、`type`（设为 `3` = 步行） |各候选的 `distance`（米）和 `duration`（秒） |
| **`maps_search_detail`** | POI 详情查询：获取更完整的 POI 信息（评分、营业时间等） | `id`（POI ID，多个用 `|` 分隔） | POI 详情，可能含 `biz_ext.rating`（评分）、`biz_ext.cost`（人均消费）等 |

### 工具选择策略

- **优先用 `maps_around_search`**（直接基于起点坐标搜索，最符合"附近"语义）
- `maps_text_search` 作为备用（周边搜索无结果或需要更宽泛范围时使用）
- **`maps_direction_walking` 是核心**（必须用它获取步行时间，不能用直线距离估算）
- `maps_distance` 可批量获取多个候选的距离时间，比逐个调 `maps_direction_walking` 更高效

## 三、执行步骤

### Step 1：理解用户需求

从用户的自然语言中提取以下结构化信息：

| 字段 | 示例 | 提取说明 |
|------|------|---------|
| **起点坐标** | `120.155507,30.274085` | 评测时由平台直接提供起点坐标，格式 `lng,lat`，无需自己定位 |
| **地点类型** | "咖啡馆"、"便利店"、"公园" | 用户需求中的关键词，直接用于搜索的 `keywords` 参数 |
| **步行时间上限** | "步行不超过 15 分钟" → `900` 秒 | 需换算为秒：分钟数 × 60 |
| **推荐数量上限** | "最多 3 家" → `3` | 取整数 |
| **排序偏好** | "优先近一点" → 按步行耗时升序 | 若无明确偏好，默认按步行耗时升序 |
| **城市** | "杭州" | 辅助搜索，周边搜索时非必需 |

**默认值（用户未明确提及时）**：
- 步行时间上限：**15 分钟（900 秒）**
- 推荐数量上限：**3**
- 排序偏好：**按步行耗时升序**

### Step 2：搜索候选地点

**首选 `maps_around_search`**，参数设置：

```json
{
  "location": "起点经纬度(lng,lat)",
  "keywords": "地点类型关键词",
  "radius": 3000,
  "offset": 15
}
```

**参数说明**：
- `location`：评测平台提供的起点坐标，格式必须为 `经度,纬度`（如 `120.155507,30.274085`）
- `keywords`：直接用用户说的地点类型词，如 "咖啡馆"、"餐厅"
- `radius`：搜索半径，单位米。用户步行时间上限 ≤ 15 分钟时设 **3000 米**（正常步行约 80-100 米/分钟，15 分钟约 1200-1500 米，留余量）
- `offset`：取前 10~15 个候选，筛选后取最多 3 个

**降级策略**（周边搜索返回 0 条）：
1. 扩大 `radius` 到 5000 米重试
2. 若仍为 0，使用 `maps_text_search`：
   ```json
   { "keywords": "地点类型", "city": "城市名" }
   ```
3. 若关键词搜索也为 0，如实告知用户"当前搜索范围内未找到符合类型的地点"

> ⚠️ **降级搜索后，必须重新执行 Step 3（查所有候选步行路线）和 Step 4（筛选排序）**，不能跳过筛选直接推荐降级搜索的结果！降级搜索的结果同样需要逐条查步行路线、逐条过滤时间上限。

### Step 3：遍历所有候选 POI 查询步行路线

**⚠️ 重要：必须对 Step 2 返回的所有候选 POI 逐一查询，不能只查前几个！**
周边搜索返回 15 个 POI 中可能前 3 个都超过 15 分钟，但第 8、12、14 个其实在范围内。**少查一个就可能漏掉合适的推荐**。

#### 3.1 对每个候选 POI 调用 `maps_direction_walking`

```json
{
  "origin": "起点经纬度",
  "destination": "候选POI的经纬度"
}
```

#### 3.2 检查工具返回状态

每次调用后**立即检查**返回值：
- 如果 `status` 字段为 `0`（失败），记录该 POI 查询失败，在最终回答中如实说明
- 如果 `status` 为 `1`（成功），正常提取数据
- 如果**所有候选都查询失败**，进入"情况 C：工具调用失败"的处理流程

#### 3.3 从成功的返回结果中提取

- `route.paths[0].distance` → 步行距离（米）
- `route.paths[0].duration` → 步行耗时（秒），换算为分钟展示

#### 3.4 批量优化（谨慎使用）

如果候选较多，**可以先用 `maps_distance` 做一轮初筛**（`type=3` 步行），快速排除明显过远的候选，然后对剩下的候选**全部用 `maps_direction_walking` 获取精确的路线时间**。

```json
{
  "origin": "起点经纬度",
  "destination": "候选1经纬度|候选2经纬度|...",
  "type": 3
}
```

> ⚠️ **题目要求"步行时间应来自路线查询"**（不是直线距离/测量）。最终用于筛选和排序的 duration **必须来自 `maps_direction_walking`**。`maps_distance` 只能作为预筛选工具，不能直接用来做最终推荐判断。

### Step 4：筛选与排序

#### 4.1 硬条件筛选（必须严格执行，**宁少勿多**）

逐条检查，**任何一条不满足则排除该 POI，绝对不能"差不多就行"或"四舍五入"**：

| 条件 | 判断规则 | 说明 |
|------|---------|------|
| **步行时间上限** | `duration < 用户设定上限（秒）` | **严格小于**。用户说"不超过 15 分钟"= 900 秒，那 899 秒可以，901 秒必须排除。**必须用 `maps_direction_walking` 返回的 duration，绝不使用直线距离或估算值** |
| **地点类型匹配** | 用户关键词在 `poi.name` 或 `poi.type` 中明确出现 | "咖啡馆"搜索返回的"咖啡吧"→ 可以收；返回的"餐厅（提供咖啡）"→ **排除**（有歧义）；如果不确定，**宁可不推荐有歧义的，也不要凑数量** |

> 💡 为什么"宁少勿多"？评测时如果硬条件违反（如推荐了超时的地点），平台规则校验直接判定"需求不满足"（30% 权重），扣分会比"少推荐一个"严重得多。

#### 4.2 排序

根据用户偏好对通过筛选的候选排序：
- **"优先近一点" / 无偏好** → 按 `duration` 升序（耗时最短在前）
- **"优先远一点"** → 按 `duration` 降序
- **其他偏好（如评分）** → 若通过 `maps_search_detail` 拿到了 `biz_ext.rating` 等字段，可结合排序；若无则仍按步行时间

#### 4.3 截断

取排序后的前 **N 个**（N = 用户指定的推荐数量上限，默认 3）。

## 四、生成推荐回答

### 4.1 推荐列表格式

使用**表格**呈现，结构清晰，方便用户快速比较：

```markdown
根据你的需求，以下是从起点出发步行可达的推荐（按步行距离由近到远排序）：

| # | 名称 | 地址 | 步行距离 | 预计步行时间 | 推荐理由 |
|---|------|------|----------|-------------|---------|
| 1 | [POI名称] | [POI地址] | X 米 | Y 分钟 | [基于数据的简短理由] |
| 2 | ... | ... | ... | ... | ... |
| 3 | ... | ... | ... | ... | ... |
```

### 4.2 推荐理由撰写原则

**每个推荐的理由必须引用该 POI 自身的高德返回数据**，不能笼统地说"这些都不错"。

| ✅ 推荐的理由写法（引用具体数据） | ❌ 错误写法（无数据支撑） |
|------|----------|
| "步行仅需 9 分钟，是搜索结果中距离最近的" | "这家很不错"、"是个好选择" |
| "步行 10 分钟可达，是第二近的候选" | "环境应该不错"、"人少" |
| "高德评分 4.5 分（来自 biz_ext.rating）" | "口碑很好"、"味道好" |

**理由撰写技巧**：
- 优先用步行数据排序位置来写（"步行距离最近"、"步行时间第二短"）
- 如果用 `maps_search_detail` 拿到了 `biz_ext.rating`，可以补充"高德评分 X.X 分"
- 不要堆砌形容词，保持简短，每个推荐理由 1 句话即可

**对高德未返回的信息，统一标注"未核实"**：

```markdown
补充说明：以上地点的营业时间、店内环境等信息未核实，建议前往前确认。
```
